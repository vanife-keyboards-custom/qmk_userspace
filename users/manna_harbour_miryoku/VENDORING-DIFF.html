Verdict: the vendored copy is near-pristine. Setting aside the manna-harbour→manna_harbour rename, we changed 7 lines of upstream code across 3 files — all of them forced by ~3 years of QMK API drift, none of them layout decisions. Everything we actually own lives in the two files Miryoku designates as user hooks (custom_rules.mk, custom_config.h), both empty upstream. The layout engine, all 10 layers, and all generated Babel data are byte-identical to upstream.

Why this fork exists at all

QMK deleted all user keymaps, users/ and layouts/community/* content on 2023-11-23 (tag user-keymaps-still-present, commit 0379d1f) and stopped accepting keymap PRs. Miryoku is therefore no longer in upstream QMK at all. miryoku_qmk is a full QMK fork whose base is QMK master at 2023-05-04; since then it has received four commits, two of them CI-only, the most recent in February 2025. Migration to External QMK Userspace has been announced but not done.

So there is no upstream to track and no sync to maintain — only a frozen snapshot to vendor and carry forward. This document records exactly what carrying it forward has cost.

Our configuration — custom_rules.mk

Upstream this file is a bare two-line license header. It is Miryoku's designated options hook, included from rules.mk. All layout choices live here as make variables, which post_rules.mk converts into -DMIRYOKU_<OPT>_<VALUE> compiler defines.

Active settings

the vanife unified layout The only deliberate deviations from stock Miryoku. Recovered from the BM40 — see docs/devices/bm40/recovered-layout.md. Applies to every board built from this userspace, which is what keeps BM40 and Corne in sync.
+MIRYOKU_ALPHAS ?= QWERTY        # stock default: COLEMAKDH+MIRYOKU_NAV    ?= INVERTEDT     # stock default: vi-style row
Why ?= and not =, and why not #define.
A keymap's rules.mk is read at build_keyboard.mk:146; this file is reached via users/rules.mk at line 429 — later. A plain = here would clobber any per-keymap value, so the userspace defaults must use ?=.
These two options were originally #defines in custom_config.h and were moved here in 2026-07. Miryoku resolves each option with a first-match #elif chain in alphabetical order (miryoku_babel/miryoku_layer_selection.h:12-33). A #define is unconditional, so a per-keymap MIRYOKU_ALPHAS=… would define a second symbol rather than replace the first, and whichever appeared earlier in the chain would win with no diagnostic. QWERTY sits 9th of 10 — COLEMAKDH would have silently overridden it, and QWERTZ would have silently lost to it. Make variables are last-write-wins and have no such hazard.

Adding a named Miryoku variant

Because the engine lives in users/ and options are make variables, a second flavour is a keymap directory that borrows the engine — no code duplication:

keyboards/crkbd/rev4_1/standard/keymaps/vanife_colemak/  keymap.c   # license header only, zero code (makes the dir discoverable)  config.h   # copy the LAYOUT_miryoku adapter from the sibling keymap  rules.mk   # USER_NAME = manna_harbour_miryoku             # MIRYOKU_ALPHAS = COLEMAKDH             # MIRYOKU_NAV    = VIqmk userspace-add -kb crkbd/rev4_1/standard -km vanife_colemak
USER_NAME is mandatory. It is what wires a differently-named keymap to this userspace. Without it the build looks for users/<keymap name>, finds nothing, and silently omits Miryoku entirely — -include does not error on a missing file. This is also why the existing vanife and vanos keymaps contain no Miryoku code: they are copies of the stock board defaults and set no USER_NAME.

Maintenance notes

  • The directory keeps upstream's name deliberately. Renaming it to vanos or similar is mechanically about six edits, but it would break diff -r against tools/miryoku_qmk — and that comparison is what makes this document, and every future QMK-drift patch, auditable.
  • The compat shims are the running cost. Upstream Miryoku is frozen at a QMK 2023-05-04 base, so every QMK breaking change from 2023-11 onward lands in custom_config.h. Bump the qmk_firmware submodule pin deliberately, not on a schedule, and re-check this file each time.
  • Keep layout and plumbing separated. Layout intent belongs in custom_rules.mk and should migrate to any future Miryoku base unchanged; custom_config.h holds only disposable shims. Do not let options drift back into custom_config.h — see the alphabetical-chain hazard above.
  • GPL housekeeping. All files retain their Copyright 2019/2022 Manna Harbour headers, satisfying GPL-2.0-or-later. custom_rules.mk carries a modification note; adding equivalent one-liners to config.h, rules.mk and manna_harbour_miryoku.c would satisfy GPLv2 §2(a) more cleanly.
  • Not yet compiled. The custom_rules.mk / custom_config.h restructure of 2026-07 has not been verified with a build. Confirm with qmk userspace-compile before flashing.
